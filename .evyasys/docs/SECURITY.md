# Security

> Generated by /evyasys:TrainDocs on 2026-06-17.

## Credential Storage

All secrets (PATs, API tokens, SMTP passwords) are stored encrypted in `~/.evyasys/credentials` — never in git.

### Encryption scheme

| Property | Value |
|---|---|
| Algorithm | AES-256-CBC |
| Key derivation | `sha256("evyasys:{hostname}:{username}")` — machine-bound |
| IV | 16 random bytes per encrypt call (`crypto.randomBytes(16)`) |
| Format | `{ivHex}:{ciphertextHex}` (one key=value pair per line) |
| File permissions | `0o600` — owner read/write only |
| Implementation | `scripts/lib/encrypt.js` |

**Threat model**: The encryption prevents casual credential exposure if the file is copied or if a backup is made. It does not protect against an adversary with physical access to the machine and the username/hostname. It is not designed as a password manager — it is designed to prevent accidental secret leakage.

**Limitation**: Because the key is derived from `hostname + username`, credentials cannot be transferred to another machine. Each developer must run `/evyasys:Setup` on each machine they use.

### Writing credentials

Always use `writeUserCreds(updates)` from `scripts/lib/config.js`. Never write to `~/.evyasys/credentials` directly.

```js
writeUserCreds({ AZURE_PAT: pat });
// writes: AZURE_PAT=<ivHex>:<ciphertextHex>
```

## What Must Never Be in Git

| Secret type | Stored in | Why it's safe |
|---|---|---|
| Azure DevOps PAT | `~/.evyasys/credentials` | Encrypted, mode 0o600, per-machine |
| JIRA API token | `~/.evyasys/credentials` | Same |
| GitHub PAT | `~/.evyasys/credentials` | Same |
| SMTP password | `~/.evyasys/credentials` | Same |
| Twilio auth token | `~/.evyasys/credentials` | Same |
| Teams webhook URL | `project.yaml` (committed) | Channel address — not a personal credential; low risk |
| Slack webhook URL | `project.yaml` (committed) | Same |

**Rule**: If a secret is personal (one credential per developer), it lives in `~/.evyasys/credentials`. If it is shared per-project (same URL for the whole team), it is safe in `project.yaml`.

## PAT Scope Requirements

Request the minimum scope needed to function:

| PM Tool | Credential | Minimum scope |
|---|---|---|
| Azure DevOps | Personal Access Token | Work Items: Read & Write |
| JIRA | API Token | Project: Browse + Create/Edit issues + Transition issues |
| GitHub | Personal Access Token | `repo` + `project:write` |

**Never** request admin, delete, or org-level scopes for normal plugin operation.

## Dry-Run Mode

`EVYASYS_DRY_RUN=1` prevents all external HTTP calls. The `runIntegration()` wrapper intercepts calls and logs `[evyasys:dry-run] {operation} args={json}` to stdout instead of executing.

Dry-run is the safest mode for CI pipelines and for testing new configurations. Local file operations (artefact saves) still execute in dry-run mode — only external API calls are skipped.

---

## Sensitive Data in Logs

**Rule**: Never log credential values. The `[evyasys:error]` and `[evyasys:dry-run]` log prefixes must not include PAT values, API tokens, or passwords.

The `runIntegration()` logs `args={JSON.stringify(args)}` — ensure that `args` passed to `runIntegration()` never includes credential fields. Credentials are in `cfg` (passed separately), not in `args`.

## Markdown Content Safety

Story content written to ADO is converted from Markdown to HTML via `scripts/lib/markdown-to-html.js`. The converted HTML is posted as the work item description field.

**Rule**: The markdown-to-HTML conversion must not introduce script injection. The content source is the AI agent output, which is internally generated — not user-supplied HTML. However, if user-provided reference documents (Path B in CreateStory) contain raw HTML, the converter must sanitise it or strip it before inclusion in the ADO payload.

**Current state**: Sanitisation is not explicitly implemented. This is a low-risk gap given that content originates from AI-generated markdown, but it should be addressed if the plugin ever processes HTML-containing reference documents.

## File Permission Verification

To verify credentials file permissions are correct:

```bash
# macOS/Linux
ls -la ~/.evyasys/credentials
# Expected: -rw------- 1 {username} ...

# Windows (PowerShell)
(Get-Item "$env:USERPROFILE\.evyasys\credentials").Attributes
# Expected: no Group/Everyone permissions
```

If permissions are wrong, re-run `scripts/login.sh` or `scripts/setup.ps1` — `writeUserCreds()` re-applies `0o600` on each write.

## Security Gaps (Remediation Required)

| Gap | Risk | Recommended fix |
|---|---|---|
| Machine-bound key uses hostname+username — predictable seed | Medium — key derivable if hostname/username known | Add a random salt to `~/.evyasys/` on first setup, combine with hostname+username |
| No HTML sanitisation in markdown-to-html converter | Low currently (AI-generated content) | Add DOMPurify or equivalent if user-supplied HTML is ever processed |
| Teams webhook URL committed to git | Low — channel address is not a credential | Acceptable by design; document clearly in project.yaml |
| No PAT expiry detection | Medium — expired PAT causes silent failures | Add expiry check in credential validation step of Setup |
