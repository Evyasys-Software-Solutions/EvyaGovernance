## Branch Naming Convention

```
feature/{command-or-scope}-{short-description}
fix/{command-or-scope}-{short-description}
chore/{scope}-{short-description}
docs/{what-is-documented}
```

Examples:
- `feature/create-story-epic-resolution` — new epic resolution logic in CreateStory
- `feature/jira-adapter` — new JIRA integration adapter
- `fix/hooks-batch-error-handling` — fix the batch abort-on-error bug
- `chore/add-jest` — add Jest test framework
- `docs/retrain-map-updates` — update doc manifest retrain map

**Rule**: Branch names must be lowercase kebab-case. No spaces, no uppercase.

---

## Commit Message Format

```
{type}: {short description in imperative present tense}

{optional body — why this change, not what it does}
```

Types:
| Type | When to use |
|---|---|
| `feat` | New command, new integration adapter, new skill capability |
| `fix` | Bug fix in hooks.js, adapter, or script library |
| `chore` | Dependency updates, config changes, non-functional tooling |
| `docs` | Changes to `.evyasys/docs/`, PROMPT.md, SKILL.md, CHECKLIST.md |
| `refactor` | Code restructuring with no behaviour change |
| `test` | Adding or updating automated tests |

Examples:
```
feat: add JIRA adapter with createEpic and createStory support

fix: prevent batch abort when individual story PM sync fails

chore: update node-fetch to 3.3.2

docs: update ARCHITECTURE.md with output block protocol table
```

## Pull Request Process

1. Create a branch from `main` following the naming convention above.
2. Make changes. Keep PRs focused on one concern.
3. Update relevant docs in `.evyasys/docs/` if the change affects architecture, rules, or standards.
4. Update `project-template/` if the change requires new files in end-user project repos.
5. Run `npm run setup` to verify the config loader still works.
6. Open PR against `main`. PR title = commit message format.
7. PR description must state: what changed, why, and any backwards-compatibility notes.
8. At least one review before merge (self-review for solo projects is acceptable with explicit rationale).

## Plugin SDLC Commands — Ordered Workflow

Every feature story in the project repository follows this sequence:

```
/evyasys:CreateStory   →  story drafted, epic resolved, board updated
/evyasys:CreateSubtask →  subtasks broken down (optional for small stories)
/evyasys:StartDev      →  tech brainstorm done, branch created, ADO → In Progress
                          (code is written here)
/evyasys:ReviewDev     →  code review checklist run
/evyasys:FinishDev     →  AC coverage checked, Dev Summary written, ADO → Ready for QA
/evyasys:StartQa       →  test plan written, ADO → In QA
                          (QA testing happens here)
/evyasys:FinishQa      →  all TCs recorded, release notes written, ADO → Done
/evyasys:GenerateReleaseNote  →  branded PDF release document produced
```

---

## ADO State Machine

```
New  →  In Progress  →  Ready for QA  →  In QA  →  Done
```

State transitions are triggered by the hooks — never manually updated in ADO when using the plugin.

---

## Merge Strategy

- Squash merge into `main` for feature and fix branches — keeps the main branch history clean.
- Merge commit for release tags.

---

## Version Lifecycle

| Step | Action |
|---|---|
| During development | Work in feature branches |
| Release candidate | Merge to `main`, update `package.json version`, tag `v{x.y.z}` |
| Hotfix | Branch from the release tag, fix, merge back to main and re-tag |
| Breaking change | Major version bump (`v2.0.0`), update ONBOARDING.md with migration notes |

## Adding a New Command — PR Checklist

- [ ] `skills/evyasys-{command}/SKILL.md` created
- [ ] `skills/evyasys-{command}/hooks.js` created
- [ ] `.ai/workflows/{command}/PROMPT.md` created with numbered steps and at least one `⛔` gate
- [ ] `.ai/workflows/{command}/AGENT.md` created
- [ ] `.ai/workflows/{command}/CHECKLIST.md` created
- [ ] Entry added to `.ai/commands.yaml`
- [ ] `ARCHITECTURE.md` updated if the command introduces a new output block type
- [ ] `EXTENSION_PATTERNS.md` updated with new hooks.js contract (if pattern differs from existing)
- [ ] `ONBOARDING.md` updated with the new command in the commands table
- [ ] Manual dry-run test with `EVYASYS_DRY_RUN=1` passes
