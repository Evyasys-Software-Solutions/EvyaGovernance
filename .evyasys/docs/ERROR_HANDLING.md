# Error Handling

> Generated by /evyasys:TrainDocs on 2026-06-17.

## Error Taxonomy

| Category | Examples | Severity | Behaviour |
|---|---|---|---|
| **Missing config** | `AZURE_ORG not set`, `No PAT available` | Fatal | Throw — hook exits, user sees message |
| **PM sync failure** | ADO 4xx/5xx, JIRA auth failed, rate limited | Non-fatal | Log warning, save locally, continue batch |
| **Notification failure** | Teams webhook 4xx, Slack unreachable | Non-fatal | Log warning, continue — notifications are fire-and-forget |
| **Parse failure** | No EVYABATCH block in agent output | Fatal | Send message to user, exit hook |
| **Missing content block** | Story ID in manifest but no `=== EVYA_STORY ===` block | Per-item skip | Log warning, mark story as skipped, continue batch |
| **File system error** | `EACCES` on local save path | Fatal | Throw — user must resolve permissions |
| **User cancellation** | User answers No to `ctx.confirm()` | Controlled | Send "Cancelled" message, exit cleanly |

## `runIntegration()` Error Pattern

All external calls (PM tool, notifications) go through `scripts/lib/dryrun.js:runIntegration()`. It never throws — it catches errors and returns them as a result object:

```js
// On success:
{ dryRun: false, name: 'devops:create-story', args: {...}, result: { id: 2345 } }

// On failure:
{ dryRun: false, name: 'devops:create-story', args: {...}, error: 'ADO POST failed: 401 Unauthorized' }

// On dry-run:
{ dryRun: true, name: 'devops:create-story', args: {...}, preview: '[evyasys:dry-run] ...' }
```

Hooks check for `.error` on the result and report to the user:
```js
if (storyResult && storyResult.id && !storyResult.error) {
  // success path
} else {
  const errMsg = (storyResult && storyResult.error) || 'PM sync failed';
  ctx.send(`⚠️  Story ${storyId} saved locally — ${pmLabel} sync failed: ${errMsg}.`);
}
```

## Local-First Recovery

Because local files are always written before PM sync, the user can resolve PM sync failures without data loss:

1. The story `.md` file already exists in `.evyasys/board/`.
2. `.ado-map.json` records the story with `adoId: null`.
3. When the PM tool is reachable again, the user can re-run the affected command or manually create the work item and update `.ado-map.json`.

**Gap**: There is no automated re-sync command for failed PM writes. This should be added as `/evyasys:Sync` in a future release.

## Missing Config Error Messages

Errors thrown when required config is absent (from `scripts/integrations/azure_devops.js`):

```
AZURE_ORG / AZURE_PROJECT not set (check .evyasys/project.yaml or env).
No PAT available. Run scripts/login.sh (macOS/Linux) or scripts/setup.ps1 (Windows) once.
```

These are intentionally descriptive and tell the user exactly what to do.

## Console Log Conventions

| Prefix | When used | Example |
|---|---|---|
| `[evyasys:dry-run]` | Any external call skipped in dry-run mode | `[evyasys:dry-run] devops:create-story args={...}` |
| `[evyasys:error]` | Any caught exception in `runIntegration()` | `[evyasys:error] devops:create-story failed: ...` |

**Rule**: Never use `console.log()` without one of these prefixes in production code paths. Debug logging must be removed before merging.

## Batch Processing — Partial Failure Handling

When a batch contains multiple stories, failures on individual items must not abort the batch:

```js
for (const story of batch.stories) {
  try {
    // ... process story
  } catch (err) {
    // This catch is for unexpected errors in the loop body
    // runIntegration() already handles PM sync errors internally
    ctx.send(`⚠️  Unexpected error processing ${story.storyId}: ${err.message}`);
    storyResults.push({ storyId: story.storyId, status: 'error', error: err.message });
    continue; // Always continue to next story
  }
}
```

**Current state**: `skills/evyasys-create-story/hooks.js` does not have a try/catch around the story loop body. If an unexpected error occurs mid-batch (e.g. `fs.writeFileSync` fails), the entire batch aborts. This should be fixed.

## User-Facing Error Messages

All user-visible error messages are sent via `ctx.send()`. They follow this format:

- Warnings (recoverable): `⚠️  {Story/Epic ID} {action} — {what happened}. {what the user should do}.`
- Batch completion with failures: Summarised in the final batch report with counts of synced / saved / failed / skipped items.

Example from `skills/evyasys-create-story/hooks.js`:
```
⚠️  Story EVYA-1042 saved locally — Azure DevOps sync failed: 401 Unauthorized.
Will sync to the PM tool automatically when the issue is resolved.
```

## Python Script Error Handling (`scripts/repo_scan.py`)

Python scripts called as subprocesses must:
- Write errors to `stderr` only — `stdout` is reserved for JSON output
- Return exit code `0` on success, non-zero on fatal error
- Never print non-JSON to `stdout` (would break the Node.js subprocess parser)

The repo scanner is called with `subprocess.check_output()` + `stderr=subprocess.DEVNULL` in the AI agent context. If it fails, the agent falls back to manual exploration.
