# Patterns

> Generated by /evyasys:TrainDocs on 2026-06-17.

## 1. Gate Pattern

A hard confirmation checkpoint before any irreversible action. The AI agent presents a summary and waits for explicit user approval. Hooks.js enforces the same gate via `ctx.confirm()`.

**Where used**: Every command that writes files or calls external APIs.

**Canonical example** — `skills/evyasys-create-story/hooks.js`:
```js
if (!(await ctx.confirm(
  `Save ${epicLine}${storyCount} story/stories to ${pmLabel}?${notifyLine}`
))) {
  ctx.send('Batch creation cancelled. All drafts are preserved in this session.');
  return;
}
```

**In PROMPT.md** — gates are marked with `⛔` and the word `GATE`:
```
## ⛔ Step 4 — Story Planning  (GATE 2 — always fires)
```

**Rule**: Every command must have at least one gate before any file is written to disk.

## 2. Delimiter-Parsing Pattern

The AI agent and hooks.js communicate through structured text blocks embedded in the AI's output. Hooks parse these blocks — not the free-form prose around them.

**Where used**: CreateStory (EVYA_STORY/EVYA_EPIC/EVYABATCH), GenerateReleaseNote (EVYARELEASE), TrainDocs (EVYADOC), Setup (EVYACONFIG).

**Canonical parser** — `skills/evyasys-create-story/hooks.js`:
```js
function parseDelimitedBlocks(text, tag) {
  const out     = {};
  const startRe = new RegExp(`=== EVYA_${tag}: ([\\w-]+) ===`, 'g');
  let   sm;
  while ((sm = startRe.exec(text)) !== null) {
    const id     = sm[1];
    const after  = text.slice(sm.index + sm[0].length);
    const endTag = `=== END_EVYA_${tag}: ${id} ===`;
    const endIdx = after.indexOf('\n' + endTag);
    if (endIdx !== -1) {
      out[id] = after.slice(1, endIdx);
    }
  }
  return out;
}
```

**Rule**: Every hooks.js must use `parseDelimitedBlocks()` or `parseBatchBlock()` — never ad-hoc regex against AI prose.

## 3. Adapter Pattern (PM Tool and Notification)

All PM operations and notifications are routed through adapter modules. The hooks.js never knows which PM tool or notification channel is active — it only calls the adapter.

**Where used**: `scripts/lib/pm-adapter.js`, `scripts/lib/notify-adapter.js`.

**Canonical example** — `scripts/lib/pm-adapter.js`:
```js
async function createStory(cfg, params) {
  if (cfg.pmTool === 'local')  return null;
  if (cfg.pmTool === 'devops') return require('../integrations/azure_devops').createStory(params);
  if (cfg.pmTool === 'jira')   return require('../integrations/jira').createStory(params);
  if (cfg.pmTool === 'github') return require('../integrations/github_board').createStory(params);
  return null;
}
```

**Rule**: Every integration adapter must export the same function names as the others for each operation so `pm-adapter.js` can route without special-casing.

## 4. Dry-Run Wrapper Pattern

Every external call (HTTP, filesystem side-effects with external impact) is wrapped in `runIntegration()`. In dry-run mode (`EVYASYS_DRY_RUN=1`), the function logs what would happen and returns without calling the real function.

**Where used**: Every `hooks.js` that calls PM tool or notification APIs.

**Canonical example** — `scripts/lib/dryrun.js`:
```js
async function runIntegration({ name, cfg, args, live }) {
  if (cfg.dryRun) {
    console.log(`[evyasys:dry-run] ${name} args=${JSON.stringify(args)}`);
    return { dryRun: true, name, args };
  }
  try {
    const out = await live();
    return { dryRun: false, name, args, result: out };
  } catch (err) {
    console.error(`[evyasys:error] ${name} failed:`, err.message || err);
    return { dryRun: false, name, args, error: String(err.message || err) };
  }
}
```

**Rule**: Never call `live()` functions outside `runIntegration()`.

## 5. Layered Config Resolution Pattern

Config values are resolved from highest-to-lowest priority source. The first source that has a value wins.

**Where used**: `scripts/lib/config.js:loadConfig()`.

**Resolution order**:
```
process.env  ──▶  ~/.evyasys/credentials  ──▶  .evyasys/project.yaml  ──▶  plugin manifest defaults
```

**Canonical example** — `scripts/lib/config.js`:
```js
const azure = {
  org: process.env.AZURE_ORG || userCreds.AZURE_ORG || (project.azure_devops && project.azure_devops.org) || '',
  pat: process.env.AZURE_PAT || userCreds.AZURE_PAT || '',
};
```

**Rule**: Every new config value must be added to `loadConfig()` following this exact resolution pattern. Never read from `process.env` directly in a hook.

## 6. Local-First Pattern

Artefact files are always written to local disk before any PM tool sync is attempted. A PM sync failure must not prevent the local file from being created, and must not abort processing of remaining items in a batch.

**Where used**: `skills/evyasys-create-story/hooks.js`, all other artefact-producing hooks.

**Canonical example** — `skills/evyasys-create-story/hooks.js`:
```js
// Save locally first (always succeeds regardless of PM status)
fs.mkdirSync(storiesDir, { recursive: true });
fs.writeFileSync(storyPath, storyContent, 'utf8');

// PM sync (may fail — does not block local save)
const storyResult = await runIntegration({ ... live: () => pm.createStory(...) });
if (storyResult && storyResult.id && !storyResult.error) {
  // back-write PM ID into local file
} else {
  ctx.send(`⚠️  Story ${storyId} saved locally — PM sync failed: ...`);
}
```

**Rule**: `fs.writeFileSync()` must always come before any `runIntegration()` call for the same artefact.

## 7. Template-Method Prompt Pattern

Every command's PROMPT.md defines numbered steps. The AI agent is the "algorithm"; the PROMPT.md is the template. The steps always follow the same macro-structure: gate input → load context → analyse → gate plan → execute → output blocks.

**Step structure used across all commands**:
```
Step 0 — Input gate (HARD GATE)
Step 1 — Load workflow context
Step 2 — {Command-specific analysis}
Step 3 — {Command-specific questions}
Step 4 — {Command-specific gate} (GATE N)
Step 5 — Execute (draft / generate / check)
Step 6 — Output structured blocks
```

**Where used**: `.ai/workflows/create-story/PROMPT.md`, `start-dev/PROMPT.md`, `finish-dev/PROMPT.md`, all other PROMPT.md files.

## 8. Back-Write Pattern

When the PM tool creates a work item and returns an ID, that ID is written back into the local markdown file. This keeps the local artefact as the single source of truth for both local content and PM tool reference.

**Canonical example** — `skills/evyasys-create-story/hooks.js`:
```js
const badge = `\n\n> **${pmLabel} Work Item:** #${storyResult.id}\n`;
let content = fs.readFileSync(storyPath, 'utf8');
if (!content.includes(`${pmLabel} Work Item:`)) {
  content = content.replace(/^(#\s+.+)$/m, `$1${badge}`);
  fs.writeFileSync(storyPath, content, 'utf8');
}
```

**Rule**: Back-write must use `!content.includes()` guard to prevent duplicate badges on re-runs.
