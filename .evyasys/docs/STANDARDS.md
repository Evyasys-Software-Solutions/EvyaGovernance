## 1. Casing Reference

### Cross-language rules (apply in every file type)

These rules are fixed regardless of language:

| Context | Rule | Example |
|---|---|---|
| Environment variable | `SCREAMING_SNAKE_CASE` | `AZURE_PAT`, `EVYASYS_DRY_RUN`, `TEAMS_WEBHOOK` |
| YAML key (project.yaml) | `snake_case` | `pm_tool`, `azure_devops`, `work_item_types` |
| YAML value (string) | double-quoted | `org: "EvyaCorp"` |
| JSON key (any .json file) | `camelCase` | `storyIdCounter`, `workflowStates`, `deliveryRules` |
| Markdown heading | Title Case for `#`; Sentence case for `##` and below | `# Technology Stack` / `## Runtime dependencies` |
| Git branch name | `kebab-case` with type prefix | `feature/jira-adapter`, `fix/batch-error` |
| Git tag | `v{semver}` | `v0.2.0`, `v1.0.0` |
| Commit type prefix | lowercase | `feat`, `fix`, `chore`, `docs`, `refactor`, `test` |

### Source code identifiers

Follow the idiomatic casing for whichever language the file is written in:

| Identifier type | Convention |
|---|---|
| Local variable | Language-idiomatic (`camelCase` in JS/TS/Go, `snake_case` in Python/Ruby) |
| Function / method | Language-idiomatic, always **verb + noun** form regardless of language |
| Class / struct / type | `PascalCase` universally |
| Module-level constant (immutable, exported) | `SCREAMING_SNAKE_CASE` universally |
| Boolean variable | Prefix with `is`, `has`, or `can` regardless of language |

Never use abbreviations unless the abbreviation is more widely known than the full word (`url`, `id`, `cfg`, `pat`, `pm`).

## 3. ID Format Rules

### Story IDs

```
{PREFIX}-{number}
```

| Field | Rule | Default | Example |
|---|---|---|---|
| `PREFIX` | Uppercase alpha only, configurable via `project.yaml → story.id_prefix` | `EVYA` | `EVYA`, `PORTAL`, `CORE` |
| Separator | always `-` (hyphen) | — | — |
| `number` | Integer, no zero-padding, starts at 1001 | — | `1001`, `1042`, `9999` |

Valid: `EVYA-1001` · `PORTAL-1234` · `CORE-1042`
Invalid: `evya-1001` (lowercase) · `EVYA_1001` (underscore) · `EVYA-001` (zero-padded)

### Epic IDs

```
EP-{number}
```

| Field | Rule | Example |
|---|---|---|
| Prefix | always `EP-` (uppercase, fixed) | `EP-` |
| Number | Zero-padded to 3 digits minimum | `001`, `042`, `100` |

Valid: `EP-001` · `EP-042` · `EP-100` · `EP-999`
Invalid: `ep-001` (lowercase) · `EP-1` (no padding) · `EPIC-001` (wrong prefix)

### Version numbers

```
v{major}.{minor}.{patch}
```

| Field | Rule |
|---|---|
| Prefix | always lowercase `v` |
| Format | semantic versioning: `{major}.{minor}.{patch}` |

Valid: `v0.2.0` · `v1.0.0` · `v2.1.3`
Invalid: `V0.2.0` (uppercase V) · `0.2.0` (no v prefix) · `v2.1` (missing patch)

## 4. Output Block Delimiter Format

Every character, space, and newline matters. Parsers match these exactly.

### Story and Epic blocks

```
=== EVYA_{TYPE}: {ID} ===
{content — starts on the very next line, no blank line gap}
=== END_EVYA_{TYPE}: {ID} ===
```

Rules:
- `TYPE` is always SCREAMING_SNAKE_CASE: `STORY` or `EPIC`
- One space between `===` and the keyword
- One space between the colon and the ID
- One space between the ID and the closing `===`
- Content begins on the line immediately after the opening delimiter — no blank line
- The closing delimiter is preceded by `\n` (the last content line ends, then the delimiter)
- No trailing spaces on any delimiter line

✅ Correct:
```
=== EVYA_STORY: EVYA-1042 ===
# EVYA-1042 — Story title

Status: Backlog
=== END_EVYA_STORY: EVYA-1042 ===
```

❌ Wrong — extra blank line after opening:
```
=== EVYA_STORY: EVYA-1042 ===

# EVYA-1042 — Story title
```

❌ Wrong — lowercase TYPE:
```
=== evya_story: EVYA-1042 ===
```

❌ Wrong — missing spaces:
```
===EVYA_STORY:EVYA-1042===
```

### EVYABATCH block

```
<!-- EVYABATCH
{
  "epics": [...],
  "stories": [...]
}
-->
```

Rules:
- `EVYABATCH` is SCREAMING_CASE, no space between `<!--` and `EVYABATCH`
- JSON starts on the line immediately after `<!-- EVYABATCH`
- JSON is pretty-printed with 2-space indent
- `-->` is on its own line, no space before it
- JSON keys are `camelCase`: `epicId`, `storyId`, `title`, `status`, `points`
- String values use double quotes

✅ Correct:
```
<!-- EVYABATCH
{
  "epics": [
    { "epicId": "EP-001", "title": "Core Platform", "status": "existing" }
  ],
  "stories": [
    { "storyId": "EVYA-1042", "epicId": "EP-001", "title": "User Login", "points": 5 }
  ]
}
-->
```

❌ Wrong — space inside comment open:
```
<!-- EVYABATCH
```
(this example is fine — the wrong version would be `<!--  EVYABATCH` with two spaces)

❌ Wrong — inline JSON (not pretty-printed):
```
<!-- EVYABATCH { "epics": [], "stories": [] } -->
```

### EVYADOC block

```
<!-- EVYADOC: FILENAME.md -->
```

Rules:
- One space after `<!--`
- `EVYADOC:` with no space before the colon
- One space after the colon
- Filename is SCREAMING_SNAKE_CASE `.md` or `{subdir}/SCREAMING_SNAKE_CASE.md`
- One space before `-->`
- Entire block is on one line

✅ Correct:
```
<!-- EVYADOC: ARCHITECTURE.md -->
<!-- EVYADOC: fe/STYLING_MICRO_STANDARDS.md -->
```

❌ Wrong:
```
<!--EVYADOC: ARCHITECTURE.md -->     (no space after <!--)
<!-- EVYADOC:ARCHITECTURE.md -->     (no space after colon)
<!-- evyadoc: architecture.md -->    (lowercase)
```

## 6. YAML Config Format (project.yaml)

### Key naming
- Top-level keys: `snake_case`
- Nested keys: `snake_case`

### Value quoting
- All string values: double-quoted
- Numeric values: unquoted
- Boolean values: unquoted lowercase (`true`, `false`)
- Empty string: `""`

### Indentation
- 2 spaces per level (never tabs)
- Nested object block: key on its own line, children indented 2 spaces

### Blank lines
- One blank line between top-level sections
- No blank lines between keys within the same section

✅ Correct:
```yaml
name: "Customer Portal"

story:
  id_prefix: "EVYA"
  velocity: 20
  point_scale: "3,5,8,13,21"

pm_tool: "devops"

azure_devops:
  org: "EvyaCorp"
  project: "CustomerPortal"
```

❌ Wrong — tabs, unquoted strings, missing blank lines:
```yaml
name: Customer Portal
story:
	id_prefix: EVYA
	velocity: 20
pm_tool: devops
azure_devops:
	org: EvyaCorp
```

## 7. JSON Format (evyaflow.json, ado-map.json, glossary.json)

### Key naming
- `camelCase` throughout
- No snake_case keys in any JSON file produced or consumed by the JS layer

### Format
- 2-space indent
- No trailing commas
- Last item in array/object: no comma
- String values: double-quoted
- Boolean: unquoted lowercase `true` / `false`
- Numbers: unquoted

✅ Correct:
```json
{
  "storyIdCounter": 1001,
  "deliveryRules": {
    "businessFirst": true,
    "dryRunByDefault": false
  }
}
```

❌ Wrong — snake_case keys, trailing comma:
```json
{
  "story_id_counter": 1001,
  "delivery_rules": {
    "business_first": true,
  }
}
```

## 8. Source Code Formatting Principles

These principles apply regardless of language. Where a language has an established community style guide (PEP 8, StandardJS, Google Style Guide, etc.), that guide governs language-specific details. The rules below cover cross-language consistency and project-level choices.

### Indentation
- Use the language's idiomatic indentation unit — never mix tabs and spaces in the same file
- Consistency within a file is mandatory; consistency across all files of the same language is required

### Line length
- Soft limit: 100 characters
- Hard limit: 120 characters — break with a continuation at the language's idiomatic point

### Blank lines
- One blank line between logical blocks within a function or method
- Language-idiomatic number of blank lines between top-level definitions
- No trailing blank lines at the end of any file
- No blank line immediately after a block-opening token (opening brace, colon, `do`, etc.)

### Import / require / include ordering

Group dependency declarations in this order with one blank line between groups:

1. Language built-ins and standard library
2. External third-party packages
3. Internal project modules

Never mix groups. One import per line.

### String literals
- Follow language convention; be consistent within a file — never mix quote styles without reason
- **JSON files always use double quotes** (mandatory per JSON spec)

### Trailing whitespace
- Never. No trailing spaces or tabs on any line in any file.

### Alignment padding (3+ parallel assignments)

When declaring 3 or more related assignments in sequence, align the `=` operators:

✅ Correct:
```
cfg    = loadConfig()
output = agentResult || ''
batch  = parseBatch(output)
```

Apply within a single logical block only. Never align across blank lines or different functional concerns.

## 10. PROMPT.md Formatting

### Step numbering
- Top-level steps: `## Step N — {Title}` (Sentence case title)
- Gate steps: `## ⛔ Step N — {Title}  (GATE N — {condition})`
- Sub-steps: `### Step Na — {Title}` (e.g., `### Step 2a — Scan existing epics`)
- Numbers are sequential with no gaps

### Gate marker format
```
## ⛔ Step 4 — Story Planning  (GATE 2 — always fires)
```
- Two spaces before `(GATE` — not one
- Gate number matches the sequence in that command (not global)
- Condition in parentheses, short phrase: `always fires` / `fires only if ≥ 1 new epic is proposed`

### Gate block content format
```
> 📋 **Action description.** Please review the table above.
>
> You can:
> - ✅ **Approve** to proceed
> - ❌ **Remove** a story (tell me the number or ID)
```

### Table format in PROMPT.md
```markdown
| Column A | Column B |
|---|---|
| value    | value    |
```
- Minimum column width: match header length
- One space inside each `|` cell

## 11. Git Branch Naming

```
{type}/{scope}-{short-description}
```

| Field | Rule | Values |
|---|---|---|
| `type` | always one of these | `feature` · `fix` · `chore` · `docs` · `refactor` · `test` |
| `/` | separator | fixed |
| `scope` | kebab-case, the command or module affected | `create-story` · `jira-adapter` · `hooks` · `config` · `encrypt` |
| `-` | separator | fixed |
| `short-description` | kebab-case, ≤ 5 words, imperative | `add-epic-resolution` · `fix-batch-abort` · `update-pat-scopes` |

Full branch name: all lowercase, hyphens only, no underscores, no slashes except the type separator.

✅ `feature/create-story-epic-resolution`
✅ `fix/hooks-batch-error-handling`
✅ `chore/add-jest-test-framework`
❌ `Feature/CreateStory` (uppercase, no scope)
❌ `feature_create_story` (underscores, no type separator)
❌ `create-story-epic-fix` (no type prefix)

## 12. Commit Message Format

```
{type}: {description in imperative present tense}
```

| Field | Rule |
|---|---|
| `type` | lowercase: `feat` · `fix` · `chore` · `docs` · `refactor` · `test` |
| `:` | colon, no space before, one space after |
| description | imperative present tense, lowercase start, no period at end, ≤ 72 chars |

✅ `feat: add JIRA adapter with createEpic and createStory`
✅ `fix: prevent batch abort when story PM sync fails`
✅ `chore: update node-fetch to 3.3.2`
✅ `docs: add ADR for machine-bound credential encryption`
❌ `Added JIRA adapter` (past tense, no type prefix)
❌ `feat: Add JIRA adapter.` (uppercase start, trailing period)
❌ `feature: add JIRA adapter` (type must be `feat`, not `feature`)

## 13. Console Log Format

Every console output from the plugin uses a bracketed prefix:

| Prefix | When | Output target |
|---|---|---|
| `[evyasys:dry-run]` | External call skipped in dry-run mode | `stdout` |
| `[evyasys:error]` | Caught exception in runIntegration | `stderr` |

Format:
```
[evyasys:dry-run] {operation} args={JSON.stringify(args)}
[evyasys:error] {operation} failed: {error.message}
```

No other prefixes. No emoji in log lines (only in `ctx.send()` user messages).

`ctx.send()` user messages use emoji only for status indicators:
- `⚠️ ` — warning (non-fatal, continues processing)
- `✅` — success
- `⛔` — hard gate / blocker

## 14. Error Message Format

Errors thrown from integration adapters follow this pattern:

```
{Integration} {METHOD} {url} failed: {status} {body}
```

Example: `ADO POST https://dev.azure.com/EvyaCorp/CustomerPortal/_apis/wit/... failed: 401 Unauthorized`

```
{CONFIG_KEY} / {CONFIG_KEY2} not set (check {location}).
No {credential} available. Run {command} to set it up.
```

Example: `AZURE_ORG / AZURE_PROJECT not set (check .evyasys/project.yaml or env).`

## 18. Markdown Artefact File Structure

Story and epic markdown files use this metadata header format before the first `##` section:

```markdown
# {ID} — {Title}

Status: {Status}
Epic: {epicId}
Story Points: {N}
Priority: {priority}
Owner:
```

Rules:
- `# {ID} — {Title}` — em-dash (`—`) with one space on each side, not a hyphen
- Metadata key-value lines: `Key: Value` — colon immediately after key, one space, then value
- One blank line between the `# heading` and the first metadata key
- One blank line after the last metadata key before the first `##`
- No bold, no markdown formatting in metadata lines — plain text only

## 19. Delimiter Parsing Implementation Rule

When implementing output block parsing logic, use named variables for every delimiter string — never inline them into search calls:

✅ Correct principle (language-agnostic):
```
startPattern = build opening delimiter pattern for tag
endTag       = build exact closing delimiter string for id
endIdx       = search text for (newline + endTag)
```

The newline character before `endTag` in the search is mandatory — the output block protocol requires the closing delimiter to begin at a line start. Do not remove this requirement without updating all PROMPT.md delimiter examples.

## 21. Code Regions and Logical Grouping

Files with more than one logical concern must be divided into clearly labelled regions using a single-line separator comment.

### Separator format

Use the language's line-comment token followed by a labelled fill line:

```
// ─── Region Name ───────────────────────────────────────────  (JS / TS / Go / Java / C#)
# ─── Region Name ────────────────────────────────────────────  (Python / Ruby / YAML / sh)
-- ─── Region Name ───────────────────────────────────────────  (SQL / Lua)
```

Rules:
- Fill character: `─` (U+2500 BOX DRAWINGS LIGHT HORIZONTAL)
- Region name is Title Case with one space on each side
- Total line length: 72 characters
- One blank line **before** the separator
- No blank line **after** the separator (first item of the region immediately follows)
- No closing separator — the next region's opening separator ends the previous region

✅ Correct:
```
// ─── Parsers ────────────────────────────────────────────────────────
function parseBatch(text) { ... }
function parseBlocks(text, tag) { ... }

// ─── Main hook ──────────────────────────────────────────────────────
module.exports = async function (ctx) { ... };
```

❌ Wrong — blank line after separator, closing separator added:
```
// ─── Parsers ────────────────────────────────────────────────────────

function parseBatch(text) { ... }
// ─── End Parsers ────────────────────────────────────────────────────
```

### When to add regions

| Condition | Add regions? |
|---|---|
| File has ≥ 2 distinctly different concerns | Yes |
| File is > 80 lines | Yes |
| File is a single-purpose utility < 50 lines | No |
| File exports only one function | No |

### Canonical region names per file type

**Command entry-point (hooks or equivalent):**

| Region | Contents |
|---|---|
| `Parsers` | output block parser functions |
| `Helpers` | internal utility functions |
| `Main hook` | the exported entry-point function |

## 22. Function and Method Comments

**The default is no comments.** Add a JSDoc block only when the exported function's parameter types or return shape are non-obvious from the name and signature alone.

### When to add a JSDoc comment

| Case | Add JSDoc? |
|---|---|
| Exported function with a non-trivial return shape | Yes |
| Exported function whose `@throws` contract is important for callers | Yes |
| Integration adapter function (the public API of the adapter) | Yes |
| Private/internal helper whose name and signature are self-explanatory | No |
| The exported function is a hooks.js main export | No — hooks are documented in PROMPT.md |

### Documentation comment format

Use the language's idiomatic documentation comment style:

| Language | Format |
|---|---|
| JavaScript / TypeScript | JSDoc `/** ... */` with `@param`, `@returns`, `@throws` |
| Python | Docstring immediately after `def` — one-line preferred, imperative tense |
| Go | Line comment immediately before the function — `// FunctionName does ...` |
| Java / C# | Javadoc / XML doc comments |
| Other | Official community documentation comment convention |

Rules that apply regardless of format:
- Describe **what the function returns**, not what it does line by line
- Document the null / undefined / empty case for the return value explicitly
- Document thrown exceptions or error states when callers must handle them
- Do not include `@author`, `@date`, or `@version` — git history has that
- Keep the comment to ≤ 8 lines; if longer, the function is probably doing too much

### Inline comment rules

Add a single `//` comment only for the **WHY**, not the WHAT:

| Situation | Comment? |
|---|---|
| Non-obvious invariant or constraint | Yes |
| Workaround for a known external bug or limit | Yes |
| Required character/whitespace that would look like a typo | Yes |
| Code that would surprise a reader on first read | Yes |
| Obvious step (`// load config`, `// loop through stories`) | Never |
| Re-stating what the next line clearly does | Never |

✅ Correct — explains why, not what:
```
// newline before endTag required — closing delimiter must begin at line start
endIdx = search(content, newline + endTag)

// idempotency guard: ADO badge may already exist from a previous run
if not content.contains('ADO: ' + result.id):
    content = content.replace(statusLine, statusLine + '\nADO: ' + result.id)
```

❌ Wrong — restates the obvious:
```
// load config
cfg = loadConfig()

// loop through stories
for story in batch.stories:
```

### Inline comment placement

- Own-line comment: same indentation as the code it precedes; no blank line between the comment and the statement it describes
- End-of-line comment: two spaces between the end of the statement and the comment delimiter, then one space before the comment text
