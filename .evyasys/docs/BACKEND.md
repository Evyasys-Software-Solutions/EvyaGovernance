# Backend

> Generated by /evyasys:TrainDocs on 2026-06-17.

## Overview

The "backend" of this project is the set of Node.js hooks and script library modules that execute after the AI agent completes. There is no HTTP server, no request/response cycle, and no database. The execution model is: **event-driven hook invocation by Claude Code**.

---

## Execution Model

```
Claude Code fires hooks.js  →  hooks.js calls loadConfig()  →
hooks.js parses AI output   →  hooks.js calls pm-adapter.js →
pm-adapter routes to adapter →  adapter calls external API  →
hooks.js calls notify-adapter.js  →  hook exits
```

All hooks are single-run processes — they start, execute, and exit. There is no persistent process.

## hooks.js Structure (per-command)

Every `skills/evyasys-{command}/hooks.js` follows this structure:

```js
// 1. Imports — always from scripts/lib/, never from integrations/ directly
const { loadConfig }     = require('../../scripts/lib/config');
const { runIntegration } = require('../../scripts/lib/dryrun');
const adoMap             = require('../../scripts/lib/ado-map');
const pm                 = require('../../scripts/lib/pm-adapter');
const notify             = require('../../scripts/lib/notify-adapter');

// 2. Parser functions (if needed) — defined at top of file
function parseDelimitedBlocks(text, tag) { ... }
function parseBatchBlock(text) { ... }

// 3. Main hook export — always async
module.exports = async function (ctx) {
  const cfg    = await loadConfig({ ctx });
  const output = ctx.agentResult || '';

  // 4. Parse structured output from AI
  const batch = parseBatchBlock(output);
  if (!batch) { ctx.send('No output block found.'); return; }

  // 5. Single confirmation gate
  if (!(await ctx.confirm(`Action description?`))) { ctx.send('Cancelled.'); return; }

  // 6. Credential check (if not local mode)
  if (cfg.pmTool !== 'local') { await pm.ensureCredentials(cfg); }

  // 7. Process items — local save first, PM sync second
  for (const item of batch.items) {
    fs.writeFileSync(itemPath, content);                       // always
    const result = await runIntegration({ live: () => pm.createStory(...) }); // may fail
  }

  // 8. Notification (fire-and-forget)
  if (cfg.notificationTool !== 'none') {
    await runIntegration({ live: () => notify.send(cfg, { event: '...' }) }).catch(() => {});
  }

  // 9. Summary report
  ctx.send(`Done — ${count} items processed.`);
};
```

## Config Object (`scripts/lib/config.js`)

`loadConfig()` returns a flat config object used by all hooks and adapters:

```js
{
  pluginRoot,          // absolute path to the plugin root (contains .ai/)
  repoRoot,            // absolute path to the active project repo (.evyasys/ lives here)
  dryRun,              // boolean — true if EVYASYS_DRY_RUN=1
  pmTool,              // 'local' | 'devops' | 'jira' | 'github'
  notificationTool,    // 'none' | 'teams' | 'slack' | 'whatsapp' | 'email'
  hasEvyasysDir,       // boolean — .evyasys/ exists in repoRoot
  hasProjectYaml,      // boolean — .evyasys/project.yaml exists
  hasDocs,             // boolean — .evyasys/docs/ exists
  isConfigured,        // boolean — project.yaml has pm_tool or legacy azure_devops block
  project: {
    name,              // human-readable project name from project.yaml
    storyIdPrefix,     // e.g. 'EVYA' — from project.yaml
    raw,               // full parsed project.yaml object
    file,              // absolute path to project.yaml
  },
  azure: { org, project, pat },
  teams: { webhook },
  jira: { domain, projectKey, email, apiToken },
  github: { owner, repo, projectNumber, token },
  slack: { webhook },
  whatsapp: { accountSid, authToken, from, to },
  email: { smtpHost, smtpPort, smtpUser, smtpPassword, from, to },
  releaseNotes: { companyName, logoPath, brandColor, outputDir, namingConvention },
  workItemTypes: { epic, story, task },
  userCreds: { file },   // path to ~/.evyasys/credentials
}
```

## Python Scripts

Python is used for utility scripts that are invoked as subprocesses by Node.js or run standalone:

| Script | Entry point | Usage |
|---|---|---|
| `scripts/repo_scan.py` | `python3 scripts/repo_scan.py` | Repo scanner — `--summary`, `--hint "keywords"`, `--story EVYA-1042 --diff` |
| `scripts/lib/evyasys_config.py` | imported by Python integrations | Python config loader for use by `.py` integration scripts |
| `scripts/lib/markdown_to_html.py` | imported | Markdown → HTML for ADO work item bodies |
| `scripts/integrations/azure_devops.py` | standalone CLI | ADO operations from Python — parallel to `.js` version |
| `scripts/integrations/teams_webhook.py` | standalone | Teams notifications from Python — parallel to `.js` version |

**Output contract for Python scripts invoked by Node.js**: must output valid JSON to stdout. Any error output goes to stderr. Never mix JSON and prose on stdout.

## ADO Integration Detail (`scripts/integrations/azure_devops.js`)

Authentication: `Basic` header with PAT encoded as `Base64(":{pat}")`.

Before posting story content to ADO, the integration strips:
1. Metadata header lines (Status, Epic, Priority, Module, Owner key-value pairs before the first `##` section)
2. The `## Confirmation` section and everything after it

This ensures ADO work items contain only the business content — not the workflow metadata. The local `.md` file is never modified; stripping is done only at post time.

## Artefact ID-to-Directory Mapping (`scripts/lib/ado-map.js`)

The file `.evyasys/.ado-map.json` persists the mapping between Evyasys IDs and:
- PM tool numeric IDs (so the hook can link child items to parents)
- Local directory paths (so subsequent commands can find the story folder)

```json
{
  "EP-001": 1001,
  "EVYA-1042": { "adoId": 2345, "dir": "/path/to/.evyasys/board/epics/EP-001/stories/EVYA-1042" }
}
```
