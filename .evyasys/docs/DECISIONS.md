## ADR-001 — Machine-Bound AES-256-CBC for Credential Encryption

**Date**: Prior to v0.2.0
**Status**: Active

**Decision**: Credentials are encrypted with AES-256-CBC using a key derived from `sha256("evyasys:{hostname}:{username}")`. The file is stored at `~/.evyasys/credentials` with mode `0o600`.

**Rationale**: A full keychain/OS credential store integration (macOS Keychain, Windows Credential Manager, Linux libsecret) would require native OS bindings and a significantly more complex dependency chain. The machine-bound key provides adequate protection against casual credential exposure from accidental file copies while keeping the implementation to 57 lines of code with no external dependencies.

**Trade-off**: The key is deterministic from known values (hostname + username). An adversary with both the file and knowledge of the machine's hostname and username could decrypt it. This is accepted because: (1) the file has restrictive permissions, (2) the primary threat model is accidental leakage, not adversarial access, and (3) adding a random salt to `~/.evyasys/` on first setup would address this with minimal complexity.

**See also**: `scripts/lib/encrypt.js`, SECURITY.md.

## ADR-002 — Local-First Artefact Saves

**Date**: Prior to v0.2.0
**Status**: Active

**Decision**: Every hooks.js must write artefact files to local disk before attempting PM tool sync. PM sync failure must never prevent local saves.

**Rationale**: External PM tools (Azure DevOps, JIRA, GitHub) are unavailable during network outages, rate-limit windows, and credential expiry. If the plugin only saved artefacts after successful PM sync, a connectivity blip would lose the AI-generated content. Local markdown files are the ground truth — PM IDs are secondary references.

**Trade-off**: Local state can diverge from PM tool state. `.evyasys/.ado-map.json` tracks `adoId: null` for unsynced items, but there is no automated re-sync. This gap is acceptable for the current user base (small teams) but should be addressed with a `/evyasys:Sync` command as scale grows.

## ADR-003 — Delimiter-Based Output Block Protocol

**Date**: Prior to v0.2.0
**Status**: Active

**Decision**: AI agent output is structured using explicit delimiters (`=== EVYA_STORY: ID ===`, `<!-- EVYABATCH {...} -->`). Hooks parse these delimiters, not the free-form prose.

**Rationale**: AI agent output is non-deterministic prose. Parsing it with regex patterns against the full text is fragile and breaks when the AI rewords its explanation. Requiring the AI to embed content in exact delimiters creates a stable contract between the AI layer and the execution layer. The AI can say anything around the delimiters; only the delimited content is processed.

**Trade-off**: The AI must be reliably instructed to produce the correct delimiters. If the AI omits or malforms a delimiter, the hook cannot recover the content. Mitigation: PROMPT.md shows exact delimiter examples; hooks produce a clear error when blocks are missing (`No EVYABATCH block found`).

## ADR-004 — Adapter Pattern for PM and Notification Tools

**Date**: Prior to v0.2.0
**Status**: Active

**Decision**: All PM tool and notification operations are routed through `scripts/lib/pm-adapter.js` and `scripts/lib/notify-adapter.js`. hooks.js never imports integration adapters directly.

**Rationale**: Without this indirection, adding a new PM tool (e.g., Linear) would require modifying every hooks.js that calls PM operations. With the adapter, adding a new tool means adding one new file under `scripts/integrations/` and two routing lines in the adapter.

**Trade-off**: An extra layer of indirection. Accepted because the adapter files are small (pm-adapter.js is ~110 lines) and the routing is transparent.

## ADR-005 — Node.js CommonJS (not ESM)

**Date**: Prior to v0.2.0
**Status**: Active

**Decision**: All Node.js files use `require()` / `module.exports` (CommonJS), not `import` / `export` (ESM).

**Rationale**: Claude Code's hook execution environment at the time of v0.2.0 development was more reliably compatible with CommonJS. `node-fetch` v3 is an ESM-only package, but can be consumed via dynamic `import()` or by pinning to a compatible version. The codebase uses `require('node-fetch')` with a fallback to native `fetch` in newer Node versions.

**Trade-off**: Cannot use `import` syntax, which is the modern standard. This should be revisited when the Claude Code hook environment confirms full ESM support.

## ADR-006 — Python for Repo Scanning

**Date**: Prior to v0.2.0
**Status**: Active

**Decision**: `scripts/repo_scan.py` is implemented in Python rather than Node.js.

**Rationale**: Python's `pathlib` and `os.walk()` are mature and well-suited to filesystem traversal. The script was authored at a time when the team had higher Python familiarity for CLI tooling. It is invoked as a subprocess from PROMPT.md step instructions, not from hooks.js.

**Trade-off**: Introduces Python as a second runtime dependency. For developers running Windows who may not have Python installed, this is an additional setup step. The scanner is non-critical — PROMPT.md instructions state "best-effort; skip on failure" — so the plugin functions without it.

## ADR-007 — Parallel Python/JS Integration Implementations

**Date**: v0.2.0
**Status**: Technical debt — see EXTENSION_PATTERNS.md refactor debt

**Decision**: `azure_devops.py` and `teams_webhook.py` exist alongside their `.js` equivalents.

**Rationale**: The Python versions were written first (batch Python-first approach) and the JS versions were added later as the hooks.js layer was developed. Both were kept during the transition.

**Trade-off**: Two implementations of the same integration create divergence risk. The JS versions are authoritative (called by hooks.js via pm-adapter.js). The Python versions are only invoked by legacy workflows. Resolution: deprecate the Python integration files and route all integration calls through the JS adapters.
