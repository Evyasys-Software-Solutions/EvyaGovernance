## Phase 1 — Technology scan

Read every config file that exists from the scan target list. For each tool or framework found, record:
- **Name** and **exact version** (from lock files or manifest)
- **Role** in the project (routing, ORM, testing, bundling, etc.)
- **Config file** where it is defined

Build a complete technology inventory before moving to Phase 2.
Do not skip any config file, even if it seems minor.

### Mandatory read sequence
1. `package.json` (or equivalent) → runtime, frameworks, dev tools, scripts
2. Lock file → exact installed versions (not ranges)
3. `tsconfig.json` → strictness settings, path aliases, target/module
4. Linting: `.eslintrc*` or `eslint.config.*` → rules, plugins, extends
5. Formatting: `.prettierrc*` → indent, quotes, semi, line length
6. Test config: `jest.config.*` or `vitest.config.*` → coverage thresholds, setup files
7. E2E: `playwright.config.*` or `cypress.config.*` → base URL, browsers, reporters
8. Database: `prisma/schema.prisma` or equivalent → models, relations, enums
9. CI/CD: `.github/workflows/**` → stages, triggers, deploy targets
10. Containers: `Dockerfile`, `docker-compose.yml` → services, ports, volumes
11. `README.md` + `CONTRIBUTING.md` → any stated conventions
12. Design system: `tailwind.config.*` or `src/styles/tokens.*` or `globals.css` → colour tokens, spacing scale, breakpoints, font sizes
13. Component library: `src/components/ui/**` → in-use library (shadcn/ui, MUI, Chakra, etc.), component variants, Storybook stories if present
14. Internationalisation: `i18n/**` or `locales/**` → i18n strategy, translation file format (if present)

## Phase 2 — Source structure scan

Use Glob to map the project layout. Record:
- Top-level directories and their inferred purpose
- Module organisation pattern: feature-based, layer-based, domain-based
- Naming conventions per file type (PascalCase, camelCase, kebab-case, snake_case)
- Import style: relative paths, absolute paths, path aliases (`@/components/...`)

### Code sampling — read 3–5 representative files per layer

| Layer | Glob pattern | What to extract |
|---|---|---|
| Components / UI | `components/**/*.tsx` (or `.vue`, `.svelte`) | Naming, prop typing, styling approach |
| Pages / Routes | `pages/**` or `app/**/page.*` or `routes/**` | Route structure, auth guards, data loading |
| API / Controllers | `api/**` or `controllers/**` | Request handling, validation, response shape |
| Services | `services/**` | Business logic pattern, dependency injection |
| Repositories / Data | `repositories/**` or `models/**` | Data access patterns, query style |
| Tests | `**/*.test.*` or `**/*.spec.*` | Test structure, assertion style, mocking approach |
| Utils / Helpers | `utils/**` or `helpers/**` or `lib/**` | Reuse patterns, error handling |

### Design system and UI pattern extraction

Read design system config files and extract concrete values — never describe the library, describe this project's implementation of it:

| Source file | What to extract |
|---|---|
| `tailwind.config.*` | Exact colour tokens (brand, neutral, semantic/status), spacing scale, breakpoints, font sizes, border-radius values — values in `theme.extend`, not Tailwind defaults |
| `src/styles/globals.css` or `src/tokens/**` | Every CSS custom property (`--var-name: value`) — name and value |
| `src/components/ui/**` | Component library in use, variants and sizes actually defined in each component |
| `*.stories.*` | Storybook stories — documented variants, args, usage patterns |

**Component library detection** — check for these patterns before writing DESIGN_SYSTEM.md:

| Library | Detection signal |
|---|---|
| shadcn/ui | `components/ui/button.tsx` + `@/components/ui` imports + `class-variance-authority` in package.json |
| Material UI | `@mui/material` in package.json |
| Chakra UI | `@chakra-ui/react` in package.json |
| Ant Design | `antd` in package.json |
| Radix UI | `@radix-ui/*` in package.json |
| Headless UI | `@headlessui/react` in package.json |
| Custom only | None of the above found |

**UX pattern detection** — scan source code for these patterns and record what library or approach is used:

| Pattern | What to look for |
|---|---|
| Loading states | Skeleton components, `isLoading` props, React Suspense, `<Loader>` / `<Spinner>` usage |
| Toast / notifications | `sonner`, `react-hot-toast`, `react-toastify`, `useToast`, `@/components/ui/toast` |
| Form library | `react-hook-form`, `formik`, `zod` resolver, `yup` schema |
| State management | `zustand`, `redux`, `jotai`, `recoil`, Context + `useReducer`, TanStack Query |
| Error boundaries | `ErrorBoundary` components, `error.tsx` (Next.js App Router), `useErrorBoundary` |
| Empty states | `EmptyState` components, "no data" / "no results" / "nothing here" patterns |
| Confirmation dialogs | `AlertDialog`, `Modal` with confirm/cancel, `window.confirm` usage |

Record all findings — they feed directly into `UI_UX_STANDARDS.md` and `DESIGN_SYSTEM.md`.

## Phase 3 — Analysis (internal — do not output)

After the scan, summarise findings privately before generating any document:

1. **Architecture pattern** — name it specifically
2. **Technology inventory** — complete list with versions
3. **Naming conventions** — one rule per file type
4. **Design patterns** — list patterns found, where each appears
5. **Testing maturity** — unit-heavy, integration-heavy, e2e-only, no tests
6. **Security posture** — auth mechanism, validation approach, known gaps
7. **Gaps and risks** — inconsistencies, missing standards, areas of concern
8. **Design system** — component library identified, exact token values extracted (colours, spacing, typography), UX patterns catalogued (loading, error, empty states, toasts, forms)

This analysis is the foundation of every document. Do not start Phase 4 until it is complete.

### Quality rules for every document

| Rule | Description |
|---|---|
| No placeholders | Never write `[TODO]`, `[TBD]`, or `<insert here>` |
| Evidence-based | Every rule cites a real file path, real config value, or real code pattern found in the scan |
| Not applicable | If a section has no evidence, write `> Not applicable — [specific reason for this project].` |
| Cross-reference | Link between related documents: `(see API_STANDARDS.md)`, `(see SECURITY.md — Authentication)` |
| Project-specific | Every document must be specific to this project — not generic internet advice |

### Output format

Wrap each document with the delimiter the hook uses to split and write files:

```
<!-- EVYADOC: FILENAME.md -->
```

Do not include a closing delimiter. Example output structure:

```
<!-- EVYADOC: STACK.md -->
# Technology Stack

> Generated by /evyasys:TrainDocs. Re-run to update after major stack changes.

...

<!-- EVYADOC: ARCHITECTURE.md -->
# Architecture

...
```

## On approval

The hook:
1. Parses the `<!-- EVYADOC: FILENAME.md -->` delimiters from this output
2. Creates `.evyasys/docs/` directory
3. Writes each document to its file
4. Generates `INDEX.md` as a navigation hub
5. Reports the list of written files

These documents become the **code quality gate** for this project.
Every `/evyasys:StartDev` run loads `ARCHITECTURE.md`, `RULES.md`, `STANDARDS.md`,
and `PATTERNS.md` from Step 0 before any brainstorm is generated.
